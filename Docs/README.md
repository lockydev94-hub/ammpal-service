## 1. What AmmPal Service Is

AmmPal Service is a **multi-service, multi-city, multi-state home-services platform** that connects
customers with verified, location-scoped service technicians, organised through a central platform
and a distributed branch network.

| | |
|---|---|
| **Primary business** | Home appliance repair |
| **Additional categories** | Cleaning, home salon, beauty parlour, plumbing, electrical, and further configured categories `[OPEN]` — this row is **not** a launch list: Cleaning and Plumbing are launch categories in `00` BO-1, and home salon and beauty parlour are inside `06` §4's "Launch Catalogue" while `17` §6 puts them in Phase 4 (`OD-DOC-28`). The launch count itself is unreconciled at 3 / 4 / 6 / 2 (`OD-DOC-27`) |
| **Launch geography** | Bhubaneswar, Odisha, India — then Cuttack and Puri subject to readiness |
| **Model** | A central platform owning configuration and standards, with company-owned and platform-partner-owned branches operating locally |
| **Monetisation** | Commission on **eligible labour** (default 15%), paid to partners on a **weekly settlement** cycle |
| **Channels** | Website, Customer app, Partner app, Control Center, toll-free voice (IVR + CCO), WhatsApp |

## 6. Critical Business Rules

These are confirmed. Changing one requires an ADR in `22` and an entry in `21`.

| # | Rule |
|---|---|
| BR-01 | A technician is **location-scoped**. Technicians register centrally; **jobs are offered by location**. |
| BR-02 | A partner branch operates **only** within its allocated territory; its dashboard is fully location-dependent. |
| BR-03 | The platform sets **minimum, maximum and default** prices. A partner may customise **only within** the band. |
| BR-04 | **Commission is charged on eligible labour only** — not on visiting charge, transport, spare parts, or customer GST. |
| BR-05 | Partners are settled **weekly**: Mon–Sun accrual, statement the following Monday, payment due within 7 calendar days. |
| BR-06 | The location hierarchy is **State → City → Zone → Service Area → Branch**. Branch is the operational unit. |
| BR-07 | Every booking resolves to exactly one service area and one branch. |
| BR-08 | Partner branches are admitted only by **Operator** or **Super Admin**. |
| BR-09 | A **branch is not a legal entity**. The invoice supplier is resolved through the branch → legal entity → tax registration for the place of supply. (`ADR-003`) |
| BR-10 | **Serviceability is a backend-resolved property** with six ordered conditions and reason codes. Google Maps proximity alone never proves it. (`ADR-004`) |
| BR-11 | A booking has **exactly one owning branch** at any instant. Transfers are audited operations. (`ADR-005`) |
| BR-12 | The **price snapshot is immutable** and is the sole basis of the final invoice. (`ADR-006`) |
| BR-13 | **Financial records are append-only** once issued. Corrections are credit/debit notes. (`ADR-015`) |
| BR-14 | **Support agents have bounded financial permissions**. Viewing a booking grants no financial capability. (`ADR-016`) |
| BR-15 | A **city becomes bookable only through an explicit activation gate**. Adding a city name changes nothing. (`ADR-017`) |
| BR-16 | All money is **integer paise**; all rates are **basis points**. No floating point in the money path. |
| BR-17 | The **backend is the only source of truth** for state, price, commission, permissions and payment status. (`ADR-013`) |
| BR-18 | **WhatsApp messages are never proof of payment or booking state.** (`ADR-014`) |

## 8. Branch, Territory & Serviceability

### 8.1 Ownership Chain

```
State (Odisha) → City (Bhubaneswar) → Branch (OD-BBI-001) → Zone → Service Area → Technician
```

A branch belongs to a **legal entity**, which holds **tax registrations** per state. A branch holds
no GST identity of its own (`ADR-003`, BR-09).

### 8.2 Serviceability — Six Ordered Conditions

A confirmed booking for a non-serviceable location is **impossible**. The API returns
`422 SERVICE_NOT_AVAILABLE` with a reason code, and the customer is offered an approved alternative.

| # | Condition | Reason code if it fails |
|---|---|---|
| 1 | The address geocodes into a known service area | `ADDRESS_NOT_GEOGRAPHABLE` |
| 2 | The area is active and owned by exactly one branch | `AREA_INACTIVE` · `AREA_UNASSIGNED` |
| 3 | The owning branch is active and the category is enabled | `BRANCH_INACTIVE` · `CATEGORY_NOT_ENABLED` |
| 4 | The legal entity holds a registration for the place of supply | `NO_TAX_REGISTRATION` |
| 5 | The service is published with a valid price band | `SERVICE_NOT_OFFERED` · `NO_PRICE_BAND` |
| 6 | At least one technician passes every hard eligibility filter | `NO_ELIGIBLE_TECHNICIAN` |

Proximity contributes only to condition 6 and to ranking. **It never satisfies conditions 1–5.**

## 11. Security & Privacy Boundaries

| Control | Rule |
|---|---|
| **Authorisation** | Role ∩ Scope ∩ Ownership, enforced server-side in SQL. Scope predicates go in the query, not in application code after fetching. |
| **Least privilege** | Explicit scope assignment; no implicit inheritance; quarterly access review. |
| **Authentication** | OTP for customers and technicians; OIDC SSO + password + MFA for staff; rotating refresh tokens with reuse detection. The MFA **scope** is `[OPEN]` — this line says "for staff", `13` §5.1 says only internal staff with financial or administrative permission, and neither reaches a partner-side settlement approver (`OD-DOC-20`). |
| **Encryption** | TLS 1.2+ everywhere; encryption at rest; application-level encryption for bank details and document numbers. |
| **Payments** | No card data ever reaches AmmPal servers. Hosted gateway checkout only. |
| **Webhook security** | HMAC over the raw body, 5-minute timestamp window, constant-time compare, dedupe by `(provider, provider_event_id)`. |
| **PII minimisation** | Every field classified. Live location retained 90 days. Call recordings 90 days, extended on dispute. |
| **Audit** | Hash-chained `audit_events`; every override in a separate log with a reason and a financial impact. |
| **Rate limiting** | Per identity and per IP; OTP limited to 5/hour/number. |
| **Separation of duties** | Settlement issue and approval held by different accounts. No account holds both `SUPER_ADMIN` and `ACCOUNTANT`. |
| **DPDP Act 2023** | Consent, minimisation, purpose limitation, retention, erasure, grievance channel, 72-hour breach notification path — **all subject to legal review**. |
| **Payment data** | PCI-DSS SAQ-A via the gateway. |

**Prohibited data**: no credentials, API keys, OTPs, card data, bank account numbers or document numbers
in logs, code, documentation or tickets.

`OD-COM-01` → `OD-COM-02` → `OD-COM-05` → `OD-DOC-01` → `OD-07-01/02/03` → `OD-DOC-02` →
`OD-DOC-12` → **`OD-DOC-38`** → `OD-14-01` → **`OD-DOC-40` → `OD-DOC-41`** → `OD-08-01/02` → `OD-DOC-22` → `OD-10-06` → `OD-DOC-20` →
`OD-DOC-13` → `OD-DOC-17` → `OD-BK-03/04` → `OD-14-05` → `OD-RM-03/04` → `OD-DOC-08`

`OD-DOC-38` is placed **before `OD-14-01`** deliberately: the ORM question is asked inside a framework,
and Prisma and Kysely are TypeScript-only choices. Answering `OD-14-01` first, then switching the
backend, re-asks it. It was also the only row in this chain that gated an act this workspace had not
performed — `git init` — **and that act has now happened, on the owner's direction of 2026-10-21**, with a
documentation-only baseline commit and an empty directory skeleton, so the row no longer gates the
*repository*; it still gates the *code*, because nothing may be written into those directories until the
framework is decided in `22` rather than inferred from `ADR-011`. `OD-DOC-39` rides with it, because the
worker's placement and its library are both consequences of the same answer.

**`OD-DOC-40` and `OD-DOC-41` sit immediately after `OD-14-01` and before anything runs, for one reason:
they are the first two rows in this chain that gate a *migration* rather than a *choice of tool*.** Once
an ORM and a framework are picked, the first schema file and the first seed script are next, and those
two questions decide what the delete path may say and whether a fixture may touch a statutory number.
Answering them later means rewriting migrations that have already been written against an assumption —
and unlike a styling or naming decision, a migration that shipped a wrong assumption has already touched
data. `OD-DOC-43` is not in this chain (it is `[IMPORTANT]`), but it decides whether the guard is real or
bypassable and whether a fourth database identity is funded, so it should be answered in the same sitting
as `OD-DOC-40` rather than separately. `OD-DOC-44` stays last and stays `[NICE]`: it cannot be answered
before `OD-10-06`, and a banner is the cheapest part of the feature.

`OD-DOC-01` sits before the GST decisions because the settlement model determines **whose** GST
treatment is at issue. `OD-DOC-02` follows `OD-07-01` rather than preceding it: the tax question
must be asked of an advisor once, with the answer already framed as a configurable default.
`OD-DOC-22` sits with the provisioning items because it is the same class of question — who may act
on production, decided before anyone is given a shell — and it must be settled before the first
`terraform apply`, not after the first runbook is written. `OD-10-06` follows the ORM and front-end
choices because those decide *where* a guard is written (Prisma middleware, Nest guard, or a policy
layer), and it precedes the catalogue items because every catalogue route needs one answer before it
can be coded. `OD-DOC-20` follows `OD-10-06` deliberately: once the token vocabulary exists, the MFA
scope can be written as a permission test rather than a list of job titles, and a scope written before
the vocabulary is decided will be written again. `OD-DOC-13` and `OD-DOC-17` are adjacent and must be
decided together: one is what a catalogue route is allowed to read, the other is whether the catalogue
has tables to read at all — deciding either alone produces a schema that cannot serve the routes or
routes that cannot be served.

The `OD-DOC-nn` items are documentation conflicts found by the audit; each carries both citations
and a recommended resolution in `21` §7. Full impact mapping: `28` §5.

`OD-DOC-34` is not in that chain because it is not upstream of the money or the guards — it is
upstream of *rendering*. It has to be answered before `34`'s prompts are run, before any artwork is
uploaded, and before the first `<img>` is coded, because the answer decides which host may appear in
`img-src` at all. Its dependency on `OD-DOC-26` (no media column in `09` §4.3) is real: storage without
a column to hold a provider reference is a CDN with nothing to serve.
